# AI Usage Billing — Production Billing Domain (revised)

## A. Audit findings (verified in code today)

- **Provider boundary is intact and must stay:** Core never touches a provider socket. `server/services/ai/index.ts` resolves config (workspace `provider_configs` → `app_runtime_config.default_ai_provider`) and delegates to the AI Runtime via `runtimeClient.runtimeComplete` / `runtimeEmbed`. Provider code lives in `runtime/ai/**`; a security test fails the build if Core imports it.
- **Single completion funnel:** all completions go through `executeAICompletion` / `executeAICompletionWithConfig`. Call sites: `server/routes/ai.ts` (`/api/ai/complete`), `server/routes/ai-agent/assistant.ts`, `server/routes/ai-agent/operatorAssist.ts`, agent engine `engine/generationStage.ts` (plus a retry call at line 282). All channels (Widget/Telegram/Bale/WhatsApp/Instagram) converge on the agent engine, so there is no channel-specific AI path.
- **Usage recording today:** `ai_usage_logs` (workspace, provider_name, model, prompt/completion/total tokens, latency, success, error_message, endpoint). No cost, currency, run grouping or rate version. Embedding/tool/retrieval calls are not logged at all.
- **Idempotency today:** in-process 5-minute memo keyed by `requestId` (`server/services/ai/idempotency.ts`). Not durable, not financial.
- **Credits today:** `deduct_ai_credits` RPC called only from `/api/ai/complete` (fixed 1 credit); `workspace_usage_counters.ai_credits_used/ai_credits_balance/ai_requests_count` per `YYYY-MM`. The engine and operator assist never deduct.
- **Single-writer rule:** `src/test/billing/singleWriterInvariants.test.ts` mandates DB triggers/functions as canonical counter writers.
- **Plan layer:** `check_workspace_entitlement`, `server/middleware/featureGating.ts`, `billing_plans.limits/entitlements`, `workspace_limit_overrides`, `PlansPage.tsx`, `PlanLockedOverlay`, `PlanUsagePanel`.

**Decision:** `ai_usage_logs` stays as the legacy analytics/compatibility projection and `ai_agent_runs` stays the operational run log. The financial domain is new, separate and append-only. Money lives only in the new ledger; billable usage truth lives only in `ai_usage_events`.

## B. Revisions applied (each item → concrete choice)

1. **Run creation at the business-operation boundary.** `ai_runs` is opened by the *caller*, not inside `executeAICompletionWithConfig`. New `server/services/ai-billing/runContext.ts` exposes `beginAiRun(...)` returning an `AiRunContext { runId, workspaceId, conversationId, channel, entryPoint, mode, reservationId }`, propagated explicitly through the agent engine (`maybeRunAiAssistantAfterVisitorMessage` opens the run before the retrieval stage) and through `AIRequest.runContext` into embeddings, retrieval, tool calls, completion and retries. `executeAICompletionWithConfig` attaches to an existing context when present and only auto-opens a standalone run when there is none (direct `/api/ai/complete`, playground, KB worker). Durable: the run row exists in the DB before any billable work, so a crash leaves a `RUNNING` row, never an invisible charge.
2. **Multi-provider runs.** `ai_usage_events` is the financial source of truth for provider/model/rate card **per component**: each row carries its own `provider`, `requested_model`, `actual_model`, `rate_card_version_id`, `component_type`, quantity and computed `provider_cost_amount`. `ai_runs` keeps only aggregate totals plus nullable `primary_provider` / `primary_model` for analytics. There is **no** single `rate_card_version_id` on `ai_runs`.
3. **Settlement vs lot allocation.** One final customer settlement per run: `ai_run_settlements` with `UNIQUE(run_id)`. Allocation across lots is a separate child table `workspace_ai_ledger_allocations (ledger_entry_id, lot_id, amount)`, so one settlement can draw partly from a plan-allowance lot and partly from purchased balance. Ledger entry totals must equal the sum of their allocations (checked by trigger and by a reconciliation test).
4. **Reservation ↔ lot consistency.** `workspace_ai_reservation_allocations (reservation_id, lot_id, amount)` reserves against specific lots. `workspace_ai_balance_lots` tracks `remaining_amount` and `reserved_amount`; `ai_expire_lots()` may only expire `remaining_amount - reserved_amount`. A lot with active reservations is marked `EXPIRING` and finishes expiring when its reservations settle or release.
5. **METER_ONLY vs fail-closed (contradiction resolved).**
   - `METER_ONLY`: missing rate card / FX / sell policy never blocks execution. Usage is recorded, the run is marked `billing_quality = UNRESOLVED` with a `billing_config_missing` reason, no ledger effect, and an admin Health alert row is created.
   - `ENFORCED`: pricing configuration is resolved **before** billable provider execution; if any of rate card / FX / policy is missing the run fails closed with `billing_rate_not_configured` / `billing_fx_not_configured` / `billing_policy_not_configured` and nothing is executed. Never silent zero cost in either mode.
6. **Under-reservation policy (explicit).** At settlement, if the actual customer charge exceeds the reservation, `ai_topup_reservation(run_id, delta)` runs atomically first. If available balance cannot cover the delta: no negative balance is created — the customer charge is capped at the reservable amount and the difference is booked to `platform_absorbed_amount` (default policy `CAP_AND_ABSORB`). A second policy value `HALT_BILLABLE_EXECUTION` is stored on the sell policy so mid-run halting can be selected later without a migration. Reservation top-up is also attempted mid-run by long multi-step runs before the next billable step.
7. **No overlapping active versions.** `ai_rate_cards`, `ai_exchange_rates`, `ai_sell_policies` each get a `tstzrange` exclusion constraint (`EXCLUDE USING gist`) on their scope key so two active windows cannot overlap. Version rotation happens inside one SQL function (`ai_publish_rate_card`, `ai_publish_exchange_rate`, `ai_publish_sell_policy`) that closes the current version and inserts the new one in a single transaction.
8. **Command-level durable idempotency (replaces `UNIQUE(run_id, charge_type)`).** New `ai_billing_commands (id, command_type, idempotency_key UNIQUE, workspace_id, run_id, request_hash, result_ref, state, created_at)`. Command types: `SETTLE_RUN`, `REFUND`, `ADJUSTMENT`, `GRANT_ALLOWANCE`, `RESERVE`, `RELEASE`. Settlement uniqueness stays `UNIQUE(run_id)` on `ai_run_settlements`; refunds and adjustments are unrestricted in count but exactly-once per client-supplied command key, so partial and repeated refunds are supported. Plan allowance grants are additionally guarded by `UNIQUE(workspace_id, billing_cycle_id, allowance_source)`.
9. **SECURITY DEFINER hardening.** Every financial function: `SET search_path = public, pg_temp`, `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role` only. All amounts, workspace ids and run ids are re-derived server-side from the authenticated principal / run row — never trusted from the client. Added to `src/test/ci/aclFunctionManifest.test.ts`.
10. **Deterministic reconciliation.** The worker promotes `ESTIMATED`/`UNRESOLVED` → `RECONCILED` **only** when authoritative usage is actually retrievable (a stored provider response with usage, or a provider-request-id lookup). Otherwise the run stays `UNRESOLVED` and is listed in admin Health. Estimated data is never relabelled as `ACTUAL`. Any delta produces a new `ADJUSTMENT` ledger entry; history is never mutated.
11. **One normalized usage extraction.** New `server/services/ai-billing/normalize.ts` is the only parser of runtime usage output. It produces the normalized component list; `ai_usage_events` is written from it, and the existing `ai_usage_logs` insert is fed from the same normalized object (legacy projection only). No second parser.
12. **Future-proof currency.** Provider cost stored as `provider_cost_amount NUMERIC(24,12)` + `provider_cost_currency` (default `USD`), with derived `provider_cost_usd` and `internal_cost_irr` stored separately alongside the FX version used. A non-USD provider price therefore needs no migration.
13. **No early rounding.** Ledger, allocations, settlements and aggregates all keep `NUMERIC(24,6)` IRR precision. Rounding to whole تومان happens only in the presentation formatter. A drift test asserts that presentation rounding never feeds back into stored balances.
14. **Precise fallback cap.** When `fallback_kind = PLATFORM_FALLBACK`, the actual normalized usage is **repriced against the user-selected model's rate card** to produce the normal-model-equivalent charge; that value is the customer charge cap, and the difference versus the real cost goes to `platform_absorbed_amount`. If the user knowingly selected a premium model, normal pricing applies with no cap.
15. **Deduplicated balance alerts.** `workspace_ai_balance_alerts` with `UNIQUE(workspace_id, billing_cycle_id, threshold)`; the alerting function inserts with `ON CONFLICT DO NOTHING` inside the same transaction that lowers the balance, so concurrent runs and retries emit one notification per threshold per cycle.

## C. Money model

- Stored currency: **IRR**, `NUMERIC(24,6)`. UI displays تومان (÷10) in the presentation layer only. Documented once; enforced by a shared formatter.
- Provider cost: `provider_cost_amount` + `provider_cost_currency` (+ normalized USD).
- No floating point anywhere in the financial path; arithmetic in Postgres `NUMERIC` or a decimal helper in TS that never round-trips through `number`.

## D. Database (additive migrations)

Catalog & pricing: `ai_models`, `ai_rate_cards`, `ai_rate_card_components`, `ai_exchange_rates`, `ai_sell_policies` — all versioned with `effective_from/effective_to`, non-overlap exclusion constraints, `created_by`, and publish-in-one-transaction functions.

Runs & usage: `ai_runs` (status `RUNNING|USAGE_RECORDED|SETTLEMENT_PENDING|SETTLED|FAILED|CANCELLED`, `billing_quality ACTUAL|ESTIMATED|RECONCILED|UNRESOLVED`, `cost_source`, `fallback_kind`, aggregate totals, `primary_provider/primary_model`, `entry_point`, `channel`), `ai_usage_events` (per-component truth incl. `raw_usage_json`), `ai_run_settlements` (`UNIQUE(run_id)`).

Wallet: `workspace_ai_wallets` (cached `available`/`reserved`), `workspace_ai_balance_lots` (`source_type`, `original_amount`, `remaining_amount`, `reserved_amount`, `billing_cycle_id`, `expires_at`, state incl. `EXPIRING`), `workspace_ai_reservations` + `workspace_ai_reservation_allocations`, `workspace_ai_ledger` (append-only, UPDATE/DELETE blocked by trigger) + `workspace_ai_ledger_allocations`, `ai_billing_adjustments`, `ai_billing_commands`, `ai_billing_audit_log`, `workspace_ai_balance_alerts`.

Financial SQL authority: `ai_reserve`, `ai_topup_reservation`, `ai_settle_run`, `ai_release_reservation`, `ai_refund_run`, `ai_grant_allowance`, `ai_expire_lots`, `ai_reconcile_wallet` — all row-locking the wallet, all command-idempotent, all hardened per item 9.

Plans: `included_ai_allowance_irr` added to plan limits and managed in the existing Plans admin UI; granted as a lot per cycle (never a balance reset).

Indexes: `(workspace_id, created_at)`, `(run_id)`, partial index on unsettled runs, `(provider, model, created_at)`, reservations `(state, expires_at)`, lots `(workspace_id, expires_at)`.

## E. Server

`server/services/ai-billing/`: `runContext.ts`, `rates.ts`, `estimate.ts`, `normalize.ts`, `ledger.ts` (typed wrappers over the SQL authority), `policy.ts` (six failure cases, fallback repricing cap, under-reservation policy), `mode.ts` (`METER_ONLY` / `ENFORCED` from `app_runtime_config`).

Lifecycle: begin run → resolve pricing (fail-closed only in ENFORCED) → estimate → atomic reserve → execute AI steps (each recording usage events under the same run) → settle once → release remainder → append ledger + allocations → update wallet projection → analytics counters (`ai_requests_count` retained).

Zero balance raises the domain error `ai_allowance_exhausted` (403) from the shared boundary, identical for every channel. A recovery worker expires stale reservations, closes orphaned `RUNNING` runs, and runs deterministic reconciliation.

APIs: workspace `GET /api/workspaces/:id/ai-billing/summary` and `/history` (final numbers only, no provider cost/FX/multiplier); admin `/api/admin/ai-billing/*` for pricing versions, runs drilldown, KPIs, adjustments/refunds and health — platform-admin only, every mutation audited.

## I. Final hardening (approved additions)

1. **Exactly-once usage ingestion.** Every billable provider attempt gets a stable identity: `ai_run_steps (id, run_id, step_kind, attempt_no, provider, requested_model, actual_model, provider_request_id, state)` with `UNIQUE(run_id, step_kind, step_seq, attempt_no)`. `ai_usage_events` carries `step_id` plus a deterministic `usage_event_key` and enforces `UNIQUE(step_id, component_type, usage_event_key)`, so re-processing a provider response, a worker retry or a duplicate callback can never double-insert a component. Ingestion is an upsert on that key.
2. **Durable idempotent run creation.** `ai_runs.operation_idempotency_key` is `UNIQUE` and derived from the business operation (workspace + inbound message id / job id / request id). `beginAiRun()` inserts with `ON CONFLICT DO NOTHING` and, on conflict, resolves and returns the existing run and its reservation — a retried inbound message or job never creates a second run or a second reservation.
3. **CAP_AND_ABSORB is not unlimited overspend.** In `ENFORCED`, each new billable step in a multi-step run must be funded first (`ai_reserve` / `ai_topup_reservation`). If funding fails, the next billable step is not executed and the run ends with `ai_allowance_exhausted` while everything already produced is settled normally. `platform_absorbed_amount` is reserved for unavoidable overage only: platform retries, platform failures, platform-controlled fallback, and post-execution deltas that could not have been prevented — never as a way to keep spending past the balance.
4. **Atomic settlement.** `ai_settle_run` performs the whole sequence in one transaction: wallet row lock → validation → settlement row → ledger entry → ledger allocations → lot mutation → reservation settle/release → wallet projection → threshold alert insert. Any failure rolls the entire transaction back; no partial financial state is possible, and the run stays recoverable in `SETTLEMENT_PENDING`.
5. **Refund semantics.** A refund reverses the original charge's allocations lot-by-lot wherever possible, supports multiple source lots and partial amounts, and is capped so that total refunds for a run never exceed the original customer charge unless an explicit admin `ADJUSTMENT` is created. If a source lot has expired, the refunded amount does **not** resurrect the expired allowance: it is credited to the workspace's active purchased-balance lot (or a new `ADJUSTMENT` lot with the current cycle's expiry) and the reason is recorded on the ledger entry.
6. **Generic FX schema.** `ai_exchange_rates(from_currency, to_currency, rate, effective_from, effective_to, created_by, version)`. The admin UI exposes USD→IRR only for now; adding a non-USD provider currency needs no migration.
7. **Pricing snapshot semantics (documented + tested).** For one run, the customer sell policy/multiplier and the billing FX are resolved **once at run start** and snapshotted immutably on the run. The provider rate card is resolved and snapshotted **per billable usage event** at the moment that step executes (a run may legitimately span several providers/models). An admin changing rates, FX or multiplier mid-run therefore has a deterministic, documented effect: it never changes the run's FX/multiplier, and it only affects rate cards for steps that start after the change.

**Additional tests:** duplicate usage ingestion (same provider response processed twice → one component set); duplicate `beginAiRun` (retried job → one run, one reservation); simulated failure at each stage of `ai_settle_run` → full rollback, no partial state; refund spanning multiple lots; refund after source-lot expiration (no resurrection); actual charge above reservation with insufficient balance (cap + absorb, never negative); multi-step run halting before an unfunded billable step; and pricing/FX/multiplier changes during an active run (FX + multiplier frozen, later steps use the new rate card).

## J. Approved final hardening (locked before implementation)

1. **`ai_usage_events` are immutable.** Ingestion is insert-only with `ON CONFLICT DO NOTHING` on `UNIQUE(step_id, component_type, usage_event_key)` — never `ON CONFLICT UPDATE`. Identical payload on the same key = no-op. A different payload on an existing key never overwrites: the run is flagged `INGESTION_CONFLICT` / `UNRESOLVED`, the conflicting payload is stored in a side table (`ai_usage_event_conflicts`) for audit, and it surfaces in Admin Billing Health.
2. **Run idempotency with payload hash.** `ai_runs` keeps `operation_idempotency_key UNIQUE` **and** a deterministic `operation_request_hash`. Same key + same hash → resume the existing run (true retry). Same key + different hash → no silent reuse: `beginAiRun` raises `idempotency_conflict`, which is logged and shown in Billing Health.
3. **Deterministic refund-after-expiration.** Refunds return value to the same source class as the original allocation: purchased-lot consumption → back to purchased balance; active plan-allowance consumption → back to that (or the equivalent current) plan-allowance lot; expired plan-allowance consumption → a new `REFUND_COMPENSATION` lot for the **current** cycle that expires at the end of that cycle. Expired allowance is never converted into purchased or non-expiring balance. Every source allocation and the refund reason stay auditable on the ledger entry and its allocations.
4. **Multi-currency FX semantics.** Two-stage, documented and tested: (a) provider currency → normalized USD using the FX snapshot resolved **per usage event** at the moment that step executes; (b) USD → IRR using the billing FX snapshotted **once at run start** and frozen for the whole run. A run may therefore span several providers and currencies and remain deterministic; an admin FX change mid-run can never make the historical or customer-facing charge ambiguous.

**Additional tests:** duplicate identical usage payload → no-op; conflicting usage payload on the same key → `INGESTION_CONFLICT`, original row untouched; same idempotency key with a different operation hash → `idempotency_conflict`; refund routed to purchased vs active-allowance vs `REFUND_COMPENSATION` lot; multi-provider/multi-currency run priced deterministically with a mid-run FX change.
