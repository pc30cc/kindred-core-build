# Enforcement Coverage Audit

_Snapshot: 2026-06-19. Generated by reading the repo, not by changing routes._

This audit lists which backend route surfaces currently use the plan-gating middleware (`requireFeature`, `requireModule`, `requireChannel`, `requireAICredits`, `requireLimit`) and which important surfaces do not.

It is intentionally cautious. **No routes were mass-edited.** Where gating is genuinely missing but the correct policy is unclear, it is documented for a future, focused pass rather than guessed.

## 1. Routes that DO use gating

| Route file | Gating used | Notes |
|---|---|---|
| `server/routes/ai.ts` (`POST /api/ai/complete`) | `requireModule('ai_assistant')` + `requireAICredits(1)` | Canonical example of full gating. |

## 2. Routes that LOOK plan-relevant but are NOT yet gated

These are obvious candidates. Gating policy is **not changed in this pass**; they are listed for future work.

| Route file | Suggested gate | Reasoning |
|---|---|---|
| `server/routes/aiAgent.ts` | `requireModule('ai_assistant')`; `requireFeature('advanced_ai_agent')` for advanced endpoints; `requireLimit('ai_kb_jobs_per_month', …)` for KB job creation | Already reads `limits.ai_kb_*` directly; should also enforce module access for non-admin paths. |
| `server/routes/aiKb.ts` | `requireModule('ai_assistant')` + `requireFeature('ai_kb_builder')` + `requireLimit('ai_kb_jobs_per_month', …)` | Reads jobsPerMonth limit but does not call middleware. |
| `server/routes/conversations.ts` | `requireLimit('max_conversations', …)` on create | Conversation creation should respect plan cap. |
| `server/routes/visitors.ts` | `requireLimit('max_visitors', …)` on tracked-visitor creation | Visitor tracking is plan-gated conceptually. |
| `server/routes/callInvitations.ts`, `callQueue.ts`, `callAvailability.ts`, `workspaceCalls.ts`, `widgetCallInvitations.ts`, `widgetCallbacks.ts` | `requireModule('voice_video')` and `requireChannel('voice')` / `requireChannel('video')` | Whole call subsystem is a plan module. |
| `server/routes/cannedResponses.ts` | `requireFeature('automation')` (or similar) | Currently ungated. |
| `server/routes/email.ts` | `requireChannel('email')` | Plan-controlled channel. |
| `server/routes/storage.ts` | `requireLimit('storage_gb', …)` on upload | Storage cap is in registry but not enforced. |
| `server/routes/widgetAttachments.ts` | `requireChannel('chat_widget')` (sanity); `requireLimit('storage_gb', …)` | Currently ungated. |
| `server/routes/notifications.ts` | None recommended now — orthogonal. | Documented for clarity. |

## 3. Routes intentionally LEFT ungated

These are correct as-is.

- All `server/routes/admin*.ts` — Super Admin surfaces must remain reachable regardless of workspace plan state.
- `server/routes/health.ts` — operational endpoint.
- `server/routes/auth.ts`, `auth-email.ts` — authentication must always work.
- `server/routes/billing.ts`, `plans.ts` — billing endpoints control the very state gating depends on; gating them would create a chicken-and-egg deadlock.
- `server/routes/account.ts`, `privacy.ts` — user-data rights routes must stay accessible.
- `server/routes/livekitWebhook.ts` and public widget bootstrap routes — access controlled by signature/CORS, not by plan.

## 4. Risks if gating were added blindly

- Locking out free-plan users from features that are intended to be free.
- Breaking widget bootstrap or call flows on workspaces not yet migrated to a plan with the corresponding module enabled.
- Creating circular dependencies between billing and gating.

## 5. Recommended next steps (out of scope for this pass)

1. For each route in §2, define the gating policy in product terms, then attach the middleware in a small focused PR per area.
2. Run `GET /api/plans/admin/diagnostics` after seeding plans to catch keys present in DB but missing from the registry.
3. Add registry coverage tests that fail CI if a new gating call references a key not present in the registry.
