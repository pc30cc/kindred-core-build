# Commerce Platform — Security Model

## Threat model summary

The Commerce Gateway talks to a merchant-controlled HTTP origin (the
WordPress site) supplied by the workspace owner. That origin is untrusted
infrastructure from Web Yar's point of view: it can be slow, malicious,
compromised, or spoofed. Conversely, the WordPress plugin talks to Web Yar,
which is untrusted from a lone WordPress installation's point of view (a
rogue actor could try to impersonate Web Yar's servers). Both directions
are authenticated; neither trusts the network.

## Identity & credential model

Each connected store gets exactly one **installation**:
`workspace_id + store_id + installation_id`, never reusable across
workspaces. The credential (`installation_secret`) is generated by Web Yar
during pairing, stored on the plugin via WordPress options with
`autoload = no`, and encrypted at rest inside Web Yar via the canonical
`server/lib/pluginCrypto.ts` (AES-256-GCM, `plugin_secrets` table, `live` /
`pending` / `previous` slots). It is never logged, never returned through
any REST response, and never embedded in the widget bootstrap config.

## Pairing (authorization-code + PKCE)

```
Plugin generates state + code_verifier (32B random, base64url)
  → code_challenge = SHA-256(code_verifier), base64url
  → opens https://<web-yar>/commerce/authorize?state=...&code_challenge=...&redirect_uri=...
  → owner logs in, picks workspace, approves permissions
  → Web Yar issues a single-use authorization code (5 min TTL)
  → redirects to the plugin's exact registered redirect_uri
  → Plugin calls POST /api/commerce/pairing/exchange with
    { code, code_verifier, installation_public_key... }
  → Web Yar verifies state was never reused, code is unexpired + unused,
    code_verifier hashes to the stored code_challenge, redirect_uri matches
    byte-for-byte
  → Web Yar creates the installation + installation_secret, marks the code
    consumed (single use, DB unique constraint + status flip in one
    statement)
  → Plugin stores the secret (encrypted) and never sees it again in plaintext
    from Web Yar
```

Implemented in `server/services/commerce/pairing.ts` /
`server/routes/commerce/pairing.ts`. State/PKCE rows live in
`commerce_pairing_requests` with a 10-minute TTL and a `consumed_at`
column enforced by a partial unique index — replay is a DB-level
impossibility, not just an application check.

## Request signing (plugin ↔ Web Yar)

Every machine request in both directions is HMAC-SHA256 signed
(`server/services/commerce/signing.ts`, mirrored in the plugin's
`Auth/RequestSigner.php`). The WordPress nonce system is CSRF protection
for admin-UI form submissions only — it is never treated as authentication
for machine calls.

Canonical string-to-sign:

```
<protocol_version>\n
<method>\n
<canonical_path>\n
<installation_id>\n
<timestamp>\n
<nonce>\n
sha256(body)
```

Headers: `X-WebYar-Installation`, `X-WebYar-Timestamp`, `X-WebYar-Nonce`,
`X-WebYar-Signature`, `X-WebYar-Protocol`.

Verification (both directions, symmetric implementation):
- Constant-time comparison (`crypto.timingSafeEqual` / PHP `hash_equals`).
- Bounded clock skew: ±300 seconds; anything outside is rejected before
  touching the signature.
- Nonce replay cache: `commerce_nonce_cache` (Web Yar side, 10-minute TTL,
  unique `(installation_id, nonce)`) / WordPress transient-backed
  `ReplayGuard.php` (plugin side). A repeated nonce within the window is
  rejected even with a valid signature.
- Body-size limit (256 KB) and `Content-Type: application/json` are
  enforced before signature verification to bound the hashing cost of an
  oversized or malformed payload.
- A modified body after signing changes `sha256(body)`, which changes the
  signature input, which fails verification — there is no separate
  "trust the body" path.

## SSRF protection (Commerce Gateway → merchant origin)

The Commerce Gateway reuses `shared/net/hostGuard.ts` unmodified:
`checkOutboundUrl()` before every call. Enforced:
- HTTPS required (no HTTP origin can be paired in production).
- Exactly one **approved origin** per installation (scheme+host+port),
  captured at pairing time and re-validated on every call — no
  per-request caller-supplied URL, no path traversal past the plugin's
  fixed `/wp-json/webyar/v1/*` routes.
- Hostname block-list (`localhost`, `*.internal`, cloud metadata hosts)
  plus IPv4/IPv6 private/loopback/link-local/multicast/reserved ranges,
  enforced both syntactically and after DNS resolution (`checkOutboundUrl`
  resolves and checks every returned address — DNS rebinding cannot bypass
  a syntactic-only check).
- Redirects are not followed by the Gateway's HTTP client
  (`server/services/commerce/httpClient.ts` sets `redirect: 'manual'`) —
  a redirect response is treated as a `commerce_invalid_response` error,
  never silently followed to a private destination.

## PII minimization

By default, Web Yar does **not** mirror full order/customer PII. Order and
customer-history tools call the plugin live, after identity verification,
and return only the fields the canonical `CommerceOrder` / masked-summary
shape defines. What is persisted: connection health, sync cursors,
idempotency/event receipts, and tool-audit metadata (`commerce_tool_audit`)
— no payment data, no full billing address, no unredacted phone/email
outside of what a verified request explicitly requires to render.

## Customer identity bridge

The plugin issues a short-lived (2 minute), single-audience, signed
assertion for a WooCommerce-logged-in visitor:
`{ installation_id, external_customer_id, issued_at, expires_at, nonce,
audience: 'webyar-widget' }`, HMAC-signed with the installation secret.
Web Yar verifies signature, installation, audience, expiry, and nonce
(replay cache, same table as request signing) before binding it to the
current widget visitor session (`server/services/widget/visitorIdentity.ts`
cookie). A tampered, expired, wrong-audience, or replayed assertion is
rejected outright; the browser is never trusted to submit a raw
`customer_id`.

## Guest order verification

Reuses the Generic Verification Core (`server/services/verification/`) —
no second OTP system. New purpose `commerce_order_lookup`
(`subjectBinding: 'commerce_order'`, `tenantBinding: 'required'`): the
visitor supplies order number + email/phone, the WooCommerce connector's
`verifyOrderContactMatch()` confirms it against the live order (masked
comparison only — the raw values never appear in a tool result before
verification), and only on a match does Web Yar issue the real OTP through
the Generic Verification Core. Order number alone is never sufficient.

## Fail-closed rules

- Membership/authorization RPC failure → 500, never silently `false`
  (mirrors `authorizeWorkspaceAccess`).
- Missing/invalid `PLUGIN_SECRETS_MASTER_KEY` → every secret operation
  throws; there is no plaintext fallback.
- Revoked installation → immediate rejection of all live reads, event
  ingestion, and AI tool execution (checked at the gateway, not only in UI).
- Unknown/un-negotiated capability → treated as absent, never assumed present.
- Ambiguous/ unauthorized order lookup → `identity_required` /
  `order_access_denied`, never partial data "to be helpful."
