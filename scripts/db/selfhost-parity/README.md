# Self-host parity generator

`database/migrations/238_selfhost_hosted_parity.sql` was generated by these
scripts. They build one scratch database per migration chain and emit every
object, column, enum value, constraint, policy, privilege and seed row the
hosted chain (`supabase/migrations`) has and the self-host chain
(`database/migrations`) lacks.

Requirements: a local PostgreSQL 15+ superuser on `127.0.0.1:55432` with
`pgvector` available, and `pg_dump` / `pg_restore` / `psql` on `PATH`.

```sh
cd scripts/db/selfhost-parity
./build.sh s_chain selfhost   # database/migrations, filename order
./build.sh h_chain hosted     # supabase/migrations, filename order
python3 gen_parity.py /tmp/parity.sql
psql -d catalog_check -f catalog.sql   # optional: the catalog listing used to diff
```

`auth_stub.sql` stands in for GoTrue's `auth` schema and applies Supabase's
default privileges, so both builds grant the way a Supabase image does and
their privileges are comparable. The generator is add-only apart from the
policy and privilege hardening described in the migration header; objects
defined differently in the two chains are reported by `catalog.sql` diffs,
not changed. Privileges only ever narrow for PUBLIC, anon and authenticated
on objects self-host already has: they keep what both chains grant.

`238` was generated from `database/migrations` before 238 and
`supabase/migrations` before `20260930100000`. To reproduce it (seed-row ids
and timestamps, and the order of the privilege blocks, differ run to run):

```sh
./build.sh s238 selfhost 238_
./build.sh h238 hosted 20260930100000
S_DB=s238 H_DB=h238 python3 gen_parity.py /tmp/parity.sql
```
